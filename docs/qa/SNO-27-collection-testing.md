Описание задачи отсутствует. Область проверки выбрана по указанию куратора:

Это технические проверки текущей реализации; окончательные критерии приёмки задачи
нужно согласовать с куратором.

## Подготовленные проверки

[`backend/tests/test_collection.py`](../../backend/tests/test_collection.py) содержит
21 тест: 6 синхронных тестов нормализации/отбора и 15 асинхронных тестов сборщика.
Используется стандартный `unittest`; тесты также можно собирать через pytest.

| Область | Ожидаемое поведение | Тесты |
| --- | --- | --- |
| Нормализация | NFKC, схлопывание пробелов, поиск без учёта регистра | `test_normalization` |
| Ранжирование | Частота по числу постов, одинаковая сущность внутри поста учитывается один раз; при равенстве сортировка по ключу | `test_frequency_is_per_post_not_per_mention`, `test_tie_is_alphabetical` |
| Фильтры | Исключены использованные, пустые, слишком длинные и низкооценённые сущности; 100 символов допустимо | `test_filters_used_blank_long_and_low_score` |
| Порог | Значения ровно на пороге 0 и 1 допустимы | `test_threshold_endpoints` |
| Неверный ML-ответ | Неверная структура, типы, NaN, бесконечность, score вне [0, 1] → `MLInferenceError` | `test_bad_model_output`, `test_malformed_ml_output` |
| Начальные записи | Посты используются напрямую; для группы owner_id отрицательный, для пользователя положительный; запрос стены ограничен 100 | `test_load_group_and_user_walls` и тесты с начальными постами |
| Дубли и пустой текст | Повторный ключ не увеличивает число записей; пробельный текст пропускается | `test_deduplication_and_blank_filter`, `test_no_new_records` |
| Нет текста | `completed`, `no_text_records`, NER не вызывается | `test_no_text_records` |
| Нет новых сущностей | `completed`, `no_new_entities` | `test_no_new_entities`, `test_used_queries_and_cached_inference` |
| Нет новых постов | `completed`, `no_new_records`; проверены параметры поискового запроса | `test_no_new_records`, `test_top_entities_limits_searches` |
| Достигнута глубина | `completed`, `max_depth`; расширение действительно доходит до второго уровня | `test_max_depth`, `test_new_entities_expand_second_level` |
| Лимит записей | `completed`, `record_limit` при загрузке начальных постов и при поиске | `test_record_limit_in_seeds_skips_ml`, `test_record_limit_during_search` |
| Кеш и запросы | Уже использованная сущность не ищется повторно; каждый пост обрабатывается NER один раз | `test_used_queries_and_cached_inference` |
| Выборка и длина | Размер NER-выборки ограничен; текст обрезается до 4000 символов; выбор воспроизводим; labels и threshold переданы | `test_sample_size_and_text_truncation` |
| Число сущностей | В поиск уходит не больше `top_entities` | `test_top_entities_limits_searches` |
| Ошибки ML | `ML_NOT_AVAILABLE`, `ML_ERROR`, `INTERNAL_ERROR`; посты сохраняются | `test_ml_failures` |
| Ошибки VK | Ошибка API, сети или разбора ответа → `failed`, `VK_ERROR`; частичные посты сохранены | `test_vk_failures_preserve_partial_records` |
| Состояние задания | Даты начала/конца заполнены, число запросов включает начальные запросы и ошибки; клиент закрывается | Общие проверки в `run_job` |

VK подменяется на уровне клиента: настоящий `VKDataSource` преобразует тестовые ответы
в `VKPost`. NER подменяется лёгким объектом. Настоящий токен, доступ в интернет,
загрузка GLiNER и запуск сервера не требуются. Для тестов лимита записей константа
временно уменьшается до 2: проверяется поведение на границе, а не нагрузка в 5000 постов.

Проверки HTTP API ведутся отдельно в SNO-16 и в эту ветку не входят.
Для выполнения SNO-27 файлы из веток SNO-16 и SNO-17 не требуются.

### Ограничения выполненных проверок

Реальный прогон проверяет техническое выполнение сценария. Он не оценивает качество
распознавания сущностей по размеченной выборке, нагрузку в 5000 записей, параллельные
задания или установку приложения. Все причины остановки и ошибки проверены
изолированными тестами в перечисленном выше объёме; в успешном реальном прогоне
подтверждена только остановка `max_depth`.

Проверки HTTP API и интерфейса относятся к SNO-16 и SNO-17 соответственно.
Для повторения сценария подготовлен `backend/scripts/check_collection_live.py`.
Он сохраняет параметры предыдущего запуска: сообщество `vk`, GLiNER, метки
`person`, `organization`, `city`, `country`, `threshold=0.5`, `max_depth=2`,
`sample_size=3`, `top_entities=1`. Используется отдельное хранилище в памяти;
запущенный сервер не требуется. Начальное сообщество загружается через `load_seeds`,
сбор выполняет настоящий `run_collection` без подмены VK и GLiNER.

Из папки `backend` ветки SNO-27, используя окружение с ML-зависимостями:

```powershell
& "C:\Users\pavel\Desktop\snowball-parsing-app\backend\.venv\Scripts\python.exe" -m scripts.check_collection_live --group vk
```

Ключ вводится в скрытом приглашении; передавать его аргументом или сохранять в коде
не требуется. При отсутствии безопасного скрытого ввода скрипт завершится ошибкой.
Проверяются итоговый статус, даты, глубина, уникальность и непустой текст записей,
отсутствие повторных поисковых запросов и согласованность счётчика VK.

Код выхода `0` означает успешные проверки с двумя достигнутыми уровнями;
`1` — ошибка; `2` — корректная ранняя остановка, при которой два уровня не достигнуты.
Первый инференс может занять время из-за загрузки модели. Секрет и тексты постов
не выводятся; детали исключений скрыты.

## Наблюдения для разработчика и куратора

### Булевый score принимается за число

`select_entities([[{"text": "city", "score": True}]], set(), 0.5, 1)` возвращает
`[("city", "city")]`. В Python `bool` является подтипом `int`, поэтому текущая
проверка допускает такой ответ модели. Это подтверждённое поведение; нужно уточнить,
требуется ли строго отклонять булевы score как неверный формат ML-ответа.

Исправления кода приложения в этой работе не вносились.
