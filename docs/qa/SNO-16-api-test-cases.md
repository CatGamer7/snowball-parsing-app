# SNO-16: тест-кейсы для точек экрана ввода токена, начальных записей и метода сравнения

Трассировка: [SNO-9 «OpenAPI-контракт точек»](https://ru.yougile.com/team/e38cdf3c8a7e/#SNO-9),
файл [`openapi.yaml`](../../openapi.yaml), версия контракта **0.2.2**.
В колонке «SNO-9» указано место в контракте, из которого следует ожидаемый результат.

Бэкенд: `http://127.0.0.1:8000`. Для описанных в OpenAPI ошибок проверяем HTTP-статус и поле `error.code`.
Поле `error.message` содержит текст для пользователя, точная формулировка может отличаться.

Колонка «Прогон» содержит результаты ручной проверки контракта 0.2.2 от 14.11.2026
и последующих прогонов; для новых результатов отдельно указаны дата и способ проверки.
«Пройден» означает, что наблюдаемый ответ соответствует ожидаемому. «Не проверялся»
означает, что этот кейс не запускали на текущей версии.

### Проверка доступа к VK перед запуском сбора

Из папки `backend`:

```powershell
py -m scripts.check_vk_access
```

Скрипт запрашивает ключ скрытым вводом и через настоящий `VKClient`/`VKDataSource`
проверяет `groups.getById`, `wall.get` и `newsfeed.search`. По умолчанию группа —
`vk`, поисковый запрос — `ТПУ`, лимит — 3 поста. Текст постов, ключ и исходные
сообщения ошибок VK не выводятся и не записываются в файл. Заглушек и ML нет.
Можно выбрать другую публичную группу: `py -m scripts.check_vk_access --group tpu_official`.

Это диагностика доступности методов VK, а не проверка `/collection/start`.
`OK` с нулём записей подтверждает только успешный запрос, но не получение постов.
`FAIL` или `SKIP` требует разбора результата до запуска полноценного сбора.
Реальный прогон пользователем 28.11.2026 прошёл: `groups.getById` — 1 сообщество,
`wall.get` — 3 поста, `newsfeed.search` — 3 поста; всего 3 запроса,
`RESULT: access checks passed`. Таким образом, для проверенного ключа доступны
все три метода. Это не подтверждает выполнение NER и завершение полного сбора.

### Проверка ошибок через запущенный backend

Из папки `backend`: `py -m scripts.check_api_validation`.
Скрипт отправляет 11 настоящих HTTP-запросов к локальному backend: VAL-04,
VAL-06–VAL-11 (два варианта VAL-09), MOD-08, GEN-01 и GEN-02.
Проверяются HTTP-статусы и предусмотренные контрактом `error.code`.
Настоящий ключ не запрашивается: используется заведомо неверная строка для VAL-04,
которую backend проверяет через настоящий VK. Для остальных запросов VK не требуется.
Сервер должен оставаться запущенным; GLiNER и заглушки не используются.
Пользователь выполнил этот набор 28.11.2026 через запущенный backend в ветке
SNO-16: `RESULT: 11 passed, 0 failed (11 requests)`. Все ожидаемые HTTP-статусы
и предусмотренные для ошибок валидации/токена `error.code` совпали. Это 10 кейсов
таблицы: VAL-09 проверен двумя отдельными запросами (число и null).

Для отдельной проверки некорректных параметров запуска:

```powershell
py -m scripts.check_api_validation --section start
```

Этот набор отправляет 31 запрос к `/collection/start`: STA-10, STA-12–STA-21,
STA-23, STA-24, STA-27 и недопустимые границы STA-28/STA-29.
Используется заведомо неверный токен; полноценный сбор и ML не запускаются.
Вариант `STA-17/string` проверяет расхождение со строгим типом `number`.
Прогон пользователем 28.11.2026: `30 passed, 1 failed (31 requests)`.
Единственный FAIL — строка `"0.5"`: получены 401 и `INVALID_TOKEN` вместо
422 и `VALIDATION_ERROR`. Остальные 30 вариантов прошли. Расхождение описано в
[`SNO-16-threshold-validation-bug.md`](SNO-16-threshold-validation-bug.md).
Положительные границы STA-28/STA-29 этим набором не покрываются.

## POST /collection/start — запуск сбора

Для реального прогона STA-03 из папки `backend` подготовлена команда:

```powershell
py -m scripts.check_wikineural_live
```

Ключ вводится скрыто. Скрипт отправляет настоящий `/collection/start` с группой
`vk` и WikiNEuRal, ожидает 202, опрашивает прогресс до `failed / ML_NOT_AVAILABLE`
и проверяет доступность непустых частичных постов через `/records`.
Согласно текущему контракту WikiNEuRal не подключена, поэтому такая ошибка задания
является ожидаемой для STA-03. GLiNER и её зависимости не нужны, заглушек нет.
Реальный прогон пользователя 28.11.2026 прошёл. Задание
`6359f24e-c9a8-4092-928e-a8c781fa3c7f` принято с HTTP 202. При опросе наблюдались
`running / records_count: 0`, затем `failed / records_count: 59` и ожидаемый
`error.code: ML_NOT_AVAILABLE`. `/records?offset=0&limit=3` вернул HTTP 200,
`total: 59`, три поста с непустым текстом; total совпал со счётчиком прогресса.
Это подтверждает STA-03 и доступность частичного результата REC-07 с настоящим VK.
Модель WikiNEuRal не выполнялась; успешный сбор с GLiNER этим прогоном не проверен.

### Подготовка и проверка настоящего GLiNER

28.11.2026 пользователь создал `backend/.venv` на Python 3.14 и установил
зависимости backend и ML. `pip check` сообщил `No broken requirements found`.
PyTorch: `2.15.0+cpu`, CUDA недоступна (CPU-сборка), импорт GLiNER успешен.
Через `services.ner.ner_extractor.extract` на тексте «Анна приехала в Москву.»
получены `Анна / person` (score около 0.9575) и `Москву / city` (около 0.9884).
Таким образом, загрузка модели и реальный инференс через адаптер проекта проверены.
Предупреждение о `torch.jit.script` на Python 3.14 не помешало этому примеру;
это не подтверждает совместимость всех возможных сценариев модели.

Для полного прогона API backend нужно перезапустить из нового окружения:
остановить прежний процесс через Ctrl+C и из папки `backend` выполнить
`.\.venv\Scripts\python.exe main.py`. В другом терминале, также из `backend`:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_gliner_live
```

Скрипт со скрытым вводом ключа запускает настоящий VK + GLiNER с группой `vk`,
labels `person`, `organization`, `city`, threshold 0.5, max_depth 1,
sample_size 1, top_entities 1. Опрашивает прогресс до 5 минут, ожидает `completed`
без ошибки с причиной `max_depth`, `no_new_entities` или `no_new_records`,
затем проверяет непустую страницу постов и согласованность счётчиков.
Пустой список новых сущностей допустим: результат зависит от реальных постов.
Ключ и тексты VK-постов не выводятся и не сохраняются скриптом.

### Реальная проверка прогресса и страниц завершённого задания

Пока backend не перезапускался, из папки `backend`:

```powershell
.\.venv\Scripts\python.exe -m scripts.check_collection_records_live --collection-id 195bc965-e8ba-47c1-992c-35812d0853cd
```

Скрипт выполняет только GET-запросы к локальному backend, без ключа, нового задания,
обращений к VK и запуска ML. Требуется завершённое по `max_depth` задание с 2–100 постами.
Проверяет 14 вариантов: PRO-03 (включая обе даты и их порядок), PRO-05, REC-02–REC-06,
значения пагинации по умолчанию на непустом наборе и последнюю неполную страницу.
Страница `limit=100` служит полной контрольной выборкой: остальные страницы сравниваются
с соответствующими срезами, проверяются поля постов и отсутствие дублей ID.
Данные постов не печатаются и не сохраняются. При отсутствии задания или ошибке
контрольной выборки зависимые проверки не запускаются; скрипт возвращает ненулевой код.
Прогон пользователем 28.11.2026 на задании `195bc965-e8ba-47c1-992c-35812d0853cd`
с 79 постами прошёл: **`14 passed, 0 failed (14 checks)`**.
Подтверждены обе даты с часовыми поясами и порядок начала/окончания,
полная контрольная страница с уникальными ID, значения по умолчанию,
точное совпадение второй записи и последней неполной страницы с контрольными срезами,
пустые страницы на конце/после конца, пять ответов 422 с `VALIDATION_ERROR`,
а также 404 с `COLLECTION_NOT_FOUND` для прогресса и постов неизвестного задания.
Для REC-02/REC-03 это реальный вариант с total=79; исходный изолированный
вариант с тремя постами сохраняется отдельно в unittest.

## Примечания к контракту

- Наблюдение для STA-17 от 21.11.2026: `StartRequest.model_validate` принимает
  `rules.threshold: "0.5"` и приводит строку к `0.5`, хотя контракт задаёт тип
  `number`, а кейс ожидает 422. Подтверждено HTTP-прогоном 28.11.2026: для строки
  получены 401 и `INVALID_TOKEN`; для -0.01, 1.01 и отсутствия поля — ожидаемые 422.
  См. [описание расхождения](SNO-16-threshold-validation-bug.md). Исправлений backend нет.

- `202` и `status: "running"` подтверждают принятие задания. Прогресс и ошибки доступны
  в `GET /collection/{collection_id}/progress`, собранные записи — в
  `GET /collection/{collection_id}/records`.
- Для STA-12 описание `POST /collection/start` задаёт `404 MODEL_NOT_FOUND` при неизвестном
  имени модели. При этом `SelectedModels.additionalProperties: false` запрещает неизвестные
  ключи на уровне схемы. В кейсе указан ожидаемый HTTP-ответ из описания точки.
