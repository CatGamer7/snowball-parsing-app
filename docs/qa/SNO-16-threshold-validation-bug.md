# SNO-16 / STA-17: строковый threshold не отклоняется

Дата подтверждения: 28.11.2026. Backend запущен пользователем из ветки
`feature/SNO-16-api-test-cases`, база `5358cd9`. Проверка выполнена настоящим
HTTP-запросом без подмен VK или HTTP-клиента.

## Воспроизведение

При работающем backend, из папки `backend`:

```powershell
py -m scripts.check_api_validation --section start
```

Проверка `STA-17/string` отправляет `POST /collection/start` с телом:

```json
{
  "token": "vk1.a.wrong",
  "seeds": [{"type": "group", "id": "vk"}],
  "rules": {
    "models": {"urchade/gliner_multi-v2.1": {"labels": ["city"]}},
    "threshold": "0.5",
    "max_depth": 2
  }
}
```

Токен намеренно несуществующий; настоящий секрет для воспроизведения не нужен.

| Проверка | Результат |
| --- | --- |
| Ожидается по `openapi.yaml`, `Rules.threshold` (`type: number`) и STA-17 | HTTP 422, `error.code: VALIDATION_ERROR` |
| Фактически по выводу пользователя | HTTP 401, `error.code: INVALID_TOKEN` |
| Остальные варианты STA-17: -0.01, 1.01, отсутствие поля | HTTP 422, `VALIDATION_ERROR`, проверки прошли |
| Весь набор параметров запуска | `30 passed, 1 failed (31 requests)` |

## Причина и влияние

Ранее отдельно подтверждено, что `StartRequest.model_validate` преобразует
строку `"0.5"` в число `0.5`. В `api/schemas.py` поле `Rules.threshold`
объявлено как `float` без строгого режима. Поэтому запрос не отклоняется
на этапе проверки типа и доходит до проверки токена через VK.

С настоящим токеном этот HTTP-сценарий пока не повторялся; принятие задания
с таким телом не объявляется проверенным. Проблема относится к согласованности
контракта и валидации, не к работоспособности введённого пользователем ключа.

Разработчику следует согласовать требуемое поведение: отклонять строковые
значения согласно текущему контракту либо явно разрешить их и обновить контракт
и кейс. Код приложения и ожидаемый результат теста в рамках QA-проверки не менялись.
